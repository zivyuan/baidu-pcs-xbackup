# 备份完整性校验与续传(对账式上传)设计

日期:2026-10-15
状态:已与用户确认

## 背景与问题

本项目使用官方开放平台三步上传(precreate → superfile2 分片 → create),
文件只在 `create` 成功后才在网盘可见,分片传一半不会留下半成品文件。
因此真正的风险不是"分片级断点",而是:

- **Gap A(误判完成)**:实测部分应用 precreate/create 可能假成功
  (upload.go 注释:`return_type=1` 但文件并未创建)。文件实际不在或大小
  不对,任务却打了完成标志。
- **Gap B(中断重跑全量)**:raw 模式中断后无 `_SUCCESS`,`IsDone=false`,
  下次整个任务从头传;秒传不可靠时重传成本是全量。

## 目标

1. 防误判:完成标志只在远端与本地对账一致后才打。
2. 续传:raw 中断重跑只补缺失/不一致的文件。
3. 手动巡检:`bpxup verify` 子命令,默认只报告,`--fix` 才重传。

不做:内容级 md5 校验(List 接口对小文件返回混淆 md5,真实 md5 需
dlink 下载,成本过高);分片级断点续传(官方 precreate 协商已覆盖大半)。

## 方案:对账式上传 + 打标前复核(已选方案 A)

无本地状态文件,每次以远端 Listing 为准对账。跨机器安全,与现有
fingerprint 设计哲学一致。备选方案(仅事后对账、本地状态清单文件)已
评估并否决,见对话记录。

## 组件设计

### 1. 对账引擎(新文件 internal/backup/reconcile.go)

纯逻辑模块,输入输出明确,不依赖上传细节:

```
期望清单: map[相对路径]大小   ← 本地 walk(与 runRaw 同规则:跳过软链/非常规文件)
实际清单: map[相对路径]大小   ← 远端递归 List(目录逐层、串行、自动翻页)
diff     = 期望中缺失 或 大小不符 的文件列表
```

- 远端有、本地无的文件(`_SUCCESS`、历史残留)不算差异——完整性只看
  "该在的都在且大小对"。
- API 成本 = 远端目录数 + 1 次 List。1 万文件、100 目录 ≈ 100 次调用,
  串行几十秒内,防限流。

### 2. raw 模式 RunTask 改造(internal/backup/backup.go)

```
ensureDir → 对账 →
  diffs 为空?→ 补 _SUCCESS(若缺)→ 完成     ← 续传:重跑自动跳过已传好的
  有 diffs → 逐个上传 → 再对账一轮 →
    仍有 diffs → 返回 error(进入外层有界重试,重试时重新对账只补缺口)
    一致 → markSuccess
```

### 3. archive 模式改造

打包 tmp → 对账远端 `tar.gz` 大小 vs tmp 大小 → 不符/缺失才上传 →
上传后再 List 复核一次,不符返回 error(有界重试)。

### 4. IsDone 不改

完成标志只在复核通过后才打,存在性即足以判定可信:
`_SUCCESS` / `tar.gz` 存在 = 该任务经过完整对账。

### 5. verify 子命令(cmd/bpxup/cmds.go 新增)

```
bpxup verify [--project p] [--task t] [--date YYYYMMDD] [--fix]
```

- 默认校验每个匹配任务的最新一份(List `<根目录>/<项目>/` 取最大日期
  目录);`--date` 指定则校验该日期(历史巡检)。
- archive 任务需重新打包一次到临时文件比大小(不打包无法得知期望大小)。
- 默认只报告:每任务输出"一致 / 缺失 n / 大小不符 n"明细;`--fix` 才
  重传(复用对账式上传,有界重试)。
- 退出码:全部一致 0;有差异(或 --fix 后仍修不完)非 0,方便脚本巡检。
- 手动命令,不发 webhook,结果直接打终端。

## 错误处理

| 场景 | 行为 |
|---|---|
| 对账中 List 失败 | 任务失败 → 有界重试 → 耗尽告警(日常)/ 报错退出(verify) |
| 重传后复核仍不符 | 同上 |
| verify --fix 修不完 | 报告剩余差异,退出码非 0 |

## 验证方式

按用户规则不自动添加测试用例:收尾跑 `go build ./...`,并手动冒烟
(造一个中断场景验证续传、删一个远端文件验证 verify --fix)。
